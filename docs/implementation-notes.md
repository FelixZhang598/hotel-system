# 实现思路与技术亮点

## 业务建模

房型是销售对象，房间是入住资源。预订先按房型和日期锁定数量，到店才分配房号。清洁影响当前是否可接待，不永久减少未来可售库存；逾期未退房仍然阻止分房。

订单状态只允许指定动作迁移，不暴露任意状态修改接口。入住同时写入住记录、订单和事件；退房同时完成订单、记录实际退房和设置待清洁。

## 正确性策略

预订覆盖 [入住日, 离店日) 每晚。每晚库存条件更新和订单写入在同一个 IMMEDIATE 写事务，任一晚不足即整体回滚。SQLite 单写者约束用于串行化读取后决策，数据库 CHECK 和唯一索引提供额外防线。WAL 改善读写并行，不意味着多个写者。

请求幂等使用用户与幂等键组合唯一约束及请求摘要；相同请求返回原订单，不同参数拒绝。状态操作通过原状态条件及逐晚 HELD→RELEASED 明细避免重复释放。

酒店日期统一由后端按 Asia/Shanghai 提供；金额按整数分保存并由服务端计算，订单保存价格快照，避免浏览器时区和客户端金额影响业务。

## 工程与验证

前后端共享文档化接口契约。Session 负责身份，CSRF 保护写请求，角色与订单归属均在后端检查。前端只对当前合法动作显示入口，提交时后端重新校验。

依照用户要求不执行单元测试；使用真实 API 请求、并发请求、数据库账实核对、构建和浏览器验收。验证的实际覆盖与限制只以 evidence/acceptance-results.md 为准。

## 有意保留的边界

- 单机部署与有限演示库存日期窗口，超出窗口不可预订。
- 无真实支付、通知、财务或身份核验。
- 逾期住客未退房可能造成已预订客人不能立即入住，由前台处理；不自动强制退房。
- Demo 账号、数据重置和开发服务器用于本地演示，不能直接当作公网生产部署方案。
